# Phase 0 Research: Molecule tree materialization store

**Feature**: 017 | **Date**: 2026-09-08

Most decisions were resolved in the design doc (PR #85, with review-driven refinements) and the clarify pass. This file restates them with rationale/alternatives per the standard template, plus two decisions this planning pass settles that the design doc left open.

## Module placement: `git/molecule_store.py`

- **Decision**: New module `src/spaex/git/molecule_store.py`, not `src/spaex/install/molecule_store.py`.
- **Rationale**: `git/` already holds `publisher_fetch.py`, whose `ensure_object()` function does exactly this pattern for the coarser bare-clone tier: run git subprocess commands, then atomically publish a directory using a temp-dir-plus-rename plus a `ManifestLockContext`-style lock. `molecule_store.py` is the same pattern one tier down (a molecule's subtree instead of the whole repo). `install/`'s modules (`manifest_lock.py`, `generation.py`, `overlay.py`, `delta.py`) are scoped specifically to the Spec-008 install-transaction machinery that stages and publishes the CONSUMER's own `.spaex/` directory — a different concern (transactional publish of spaex's own output) from this feature (caching a read-only copy of PUBLISHER content).
- **Alternatives considered**: `install/molecule_store.py` (rejected: would blur the transaction-publish boundary that `install/` currently represents cleanly — `constitution/resolve.py`, which calls into this new module, is itself outside `install/`, so a module both `resolve.py` and the future Spec-016 `install/hook_runner.py` depend on is better placed in the more foundational `git/` layer than nested under `install/`).

## `full_sha()` return-value capture

- **Decision**: `molecule_store.py`'s public entry point accepts an already-canonical revision as an explicit precondition (documented in the function contract), and `constitution/resolve.py`'s call site is corrected to capture `git_revparse.full_sha()`'s return value and use it for every subsequent operation (the store call, `ConstitutionSource.revision`, collision tracking) rather than the original `revision` variable.
- **Rationale**: verified in this session that the existing `resolve.py` line 77 (`git_revparse.full_sha(repo_dir, revision)`) calls the function but discards its return value, continuing to use the original `revision` string for all subsequent work. This is currently harmless only because `.spaex/manifest.json`'s schema already constrains `compounds[].revision` to a full 40-hex SHA pattern before it ever reaches this code — so `full_sha()` is presently a no-op verification, not a normalization step, in practice. This spec introduces the FIRST caller (`get_or_extract`) for which failing to capture the canonical form would be a real correctness bug (a mismatched cache key for the same logical revision, if the input string ever differed in case or form from git's canonical output). Fixed at the point of introduction rather than left for a future bug report.
- **Alternatives considered**: Leave `resolve.py`'s existing discarded-return-value bug alone and have `molecule_store.py` re-derive canonical form independently (rejected: two independent canonicalization call sites for the same revision is worse than fixing the one call site that needed fixing, and leaves the underlying latent bug in place for whenever schema validation is ever bypassed or relaxed).

## Extraction mechanism: `git archive` piped into stdlib `tarfile`

- **Decision**: `git archive <sha> -- <molecule_path>` run against the bare clone, output captured as bytes, extracted via `tarfile.open(fileobj=io.BytesIO(...))` with manual member-by-member validation before each `extract()` call (see "Path-safety" below) — never `tarfile.extractall()` unfiltered, and never shelling out to an external `tar` binary.
- **Rationale**: matches the project's `py3-none-any` wheel target (no external non-git binary dependency). `git archive`'s own exit-code behavior, verified empirically this session, cleanly distinguishes "molecule path does not exist at this revision" (exit 128, `fatal: pathspec '...' did not match any files`) from "molecule path exists but is empty" (exit 0, tar stream present but perhaps trivial) — no additional existence pre-check is needed before invoking `git archive`; its own exit code is the FR-004 "not found" signal.
- **Alternatives considered**: `git worktree add` or a full `git checkout` into a scratch directory (rejected: checks out the ENTIRE repository, not just the requested molecule path — wasteful for a multi-molecule publisher repo, and working-tree checkouts have their own concurrency hazards `git archive`'s stateless stream-then-extract approach avoids). Shelling out to the `tar` binary after `git archive` (rejected: adds a dependency the project doesn't otherwise have; `tarfile`'s manual-validation path is not meaningfully harder to implement than shell-piping and keeps everything in-process and testable without subprocess mocking for the extraction step itself).

## Stable source identity for the cache key

- **Decision**: `get_or_extract()` accepts the canonical `source_url` alongside the existing bare `repo_dir`. The cache key is `(source_url, canonical_revision, molecule_path)`, and `<source-digest>` is derived as `clone_dir(state_root, source_url).name`, using the exact SHA-256-hex-16 scheme already used by the repository cache.
- **Rationale**: a local repository path is device-specific and can differ for two clones of the same source. Deriving the molecule-store key from `repo_dir` would therefore create inconsistent cache partitions and make the cache identity depend on filesystem layout. The caller already has the canonical source URL in the consumer manifest, so passing it explicitly keeps the mapping stable and testable.
- **Alternatives considered**: derive the digest from `repo_dir` (rejected: violates device-independent identity) or pass only a precomputed digest (rejected for this API: it duplicates the helper's mapping responsibility at every caller and makes source/digest mismatches easier to introduce).

## Path-safety: manual tar-member validation, archive order, absolute-path refusal

- **Decision**: For each tar member, in archive order: (1) reject if the member's own path (after normalization) is not a strict descendant of the destination directory (`..`-escape check, matching FR-010); (2) for symlink/hardlink members, reject if the link target is an absolute path (FR-011's clarification — unconditional, no resolution needed, a simple string-shape check); (3) for symlink/hardlink members with a relative target, resolve the target against the member's own directory and reject if the resolved path is not a strict descendant of the destination (FR-011's base case); (4) track which destination paths have been established as "safe" so far, and refuse any member whose parent path traverses through an EARLIER member that was itself refused or that is itself a not-yet-validated link (FR-012's archive-order requirement, defeating the "sandwich" attack from User Story 3 Acceptance Scenario 3).
- **Rationale**: Python's `tarfile.extractall(filter="data")` (3.12+) would perform an equivalent check automatically, but this project's stated minimum is 3.10. Manual validation is therefore load-bearing, not merely a defensive extra. The FR-012 archive-order requirement specifically defeats a known real-world tar-extraction attack class (an early entry creates a symlink pointing outside the destination; a later entry's path traverses through that symlink to also escape) that a naive per-entry-independent check (validate each entry in isolation, without tracking prior entries' effect) would miss.
- **Alternatives considered**: Rely solely on `tarfile.extractall(filter="data")` and simply require Python 3.12+ (rejected: contradicts the project's stated 3.10+ baseline, established well before this feature and not this feature's call to unilaterally change). A permissive absolute-path-symlink policy (resolve-then-check instead of unconditional refusal) was explicitly rejected during the 2026-09-08 clarify pass — see spec.md's Clarifications section.

## Atomicity and cache-key layout

- **Decision**: `revision_root = SPAEX_STATE/molecule-store/<source-digest>/<canonical-revision>/`; `final_dir = revision_root / molecule_path`. Extract into a temp directory sibling of `revision_root` (not of `final_dir` — an ambiguity in the design doc's first draft that its own review pass corrected), preserving the archive's `molecule_path`-prefixed structure, validate every member per the above, then atomically rename the temp directory's `molecule_path` child into `final_dir`. If a successful archive contains no members, explicitly create the empty `molecule_path` directory in the temp tree before the atomic rename. A `ManifestLockContext`-style lock (matching `publisher_fetch.ensure_object`'s per-target lock-file pattern) guards the whole acquire-check-extract-publish sequence, keyed off `final_dir`. Presence of `final_dir` (post-lock, post-check) is itself the cache-hit signal — matching `ensure_object`'s own "check existence, inside the lock, before doing the expensive work" pattern.
- **Rationale**: mirrors an already-proven pattern in this codebase (`publisher_fetch.ensure_object`) rather than inventing a new one. The corrected temp-dir-parent detail (sibling of `revision_root`, not of `final_dir`) matters because the archive's own tar entries already carry the `molecule_path` prefix — extracting them into a temp dir and renaming the WHOLE temp dir to `final_dir` would silently produce a directory nested one level too deep (`final_dir/molecule_path/...` instead of `final_dir/...`), violating FR-002.
- **Alternatives considered**: Extract directly into `final_dir` without a temp-dir stage (rejected: violates FR-009's crash-safety requirement — a killed process mid-extraction would leave a partial, but present, `final_dir` that a later request would wrongly treat as a valid cache hit).

## Error-contract translation for `constitution/resolve.py`

- **Decision**: `resolve.py`'s migrated call sites translate `molecule_store` failures as follows: a `get_or_extract()` failure meaning "the requested molecule path doesn't exist at this revision" (i.e., `git archive` exited 128) → `MissingAtomManifestError` (same error the pre-migration `git show`-based read raised for the equivalent condition). A subsequent read of `manifest.json` or a declared constitution-body file from the now-materialized directory that finds the file absent → the same existing error appropriate to that read (`MissingAtomManifestError` for the manifest, `ContributionFileNotFoundError` for a declared-but-absent constitution file). Any OTHER unexpected failure during extraction (malformed tar stream, disk-full, permission error, or a rejected-for-safety member per User Story 3) → the new `MoleculeTreeExtractionError`, never silently folded into one of the "not found" categories, and never left as a raw `tarfile`/`subprocess` exception escaping `resolve_constitution_contributions()`.
- **Rationale**: preserves FR-019's requirement that existing callers/tests of `resolve_constitution_contributions()` see no new failure categories for scenarios they already handle, while still surfacing genuinely new failure modes (extraction-specific IO/safety failures) distinctly rather than mis-reporting them as "not found."
- **Alternatives considered**: Introduce a single new umbrella error for all `molecule_store` failures, including "not found" (rejected: would force every existing caller/test that currently catches `MissingAtomManifestError`/`ContributionFileNotFoundError` to also learn a new exception type for a scenario they already handle correctly — directly contradicts FR-019 and User Story 4's non-regression goal).

## Migration boundary: what moves, what stays

- **Decision**: Publisher ROOT manifest reads (`git_show.show_bytes(repo_dir, revision, "manifest.json", ...)`) stay unchanged — needed to discover a molecule's declared path before materialization of that specific molecule is even possible. Per-molecule manifest reads and constitution-body reads move to `get_or_extract()` plus direct filesystem reads from the returned directory. `cli/add.py`'s own validation-time `git_show` reads (existence checks, workflow-category conflict checks performed before writing `.spaex/manifest.json`) are explicitly untouched — a different concern (single-file validation, no tree materialization need) from content resolution.
- **Rationale**: restated from the design doc; re-verified in this planning pass by reading `cli/add.py` directly — confirmed it has its own independent `git_show.show_bytes` call sites (lines ~54, ~77, ~200, ~204, ~218) serving adoption-request validation, structurally separate from `resolve.py`'s later full-resolution pass performed by the `spaex install` that `spaex add` delegates to.
- **Alternatives considered**: Migrate `cli/add.py` too, for full consistency (rejected in the design doc's original scoping decision and re-affirmed here: no behavioral benefit, adds extraction overhead to a validation path that only ever needs one small JSON file).

## Testing approach: crafted `tarfile.TarInfo` fixtures over real git repos for safety tests

- **Decision**: User Story 3's crafted-malicious-content tests (path traversal, symlink/hardlink escape, chained/indirect escape) are built directly using Python's `tarfile` module to construct `TarInfo` entries with arbitrary paths and link targets, rather than attempting to commit such entries into a real git repository and extract them via `git archive`. User Story 1/2/4 tests use real, small git repositories (matching `test_resolve.py`'s existing fixture-helper pattern) since those stories are about normal, well-formed content.
- **Rationale**: git itself refuses to track certain malicious constructs directly (e.g., a tracked absolute-path symlink is possible, but constructing every combination needed for FR-010 through FR-013's acceptance scenarios via actual git commits is more effort and less precise than directly authoring the tar stream that `molecule_store.py`'s validation logic must reject — the validation logic operates on the tar stream's structure, so testing it directly against constructed tar streams is the more faithful and portable test strategy, and avoids the tests depending on git's own willingness to commit a particular kind of entry in the first place.
- **Alternatives considered**: Construct malicious content via real git commits and `git archive` end-to-end (rejected as the primary strategy for the safety-refusal tests specifically, though at least one true end-to-end test — real git repo through real `git archive` through the validation logic — is still valuable as an integration-style sanity check that the two pieces connect correctly; left to `/speckit-tasks` to decide whether that sanity check is a separate task or folded into the crafted-fixture suite).
