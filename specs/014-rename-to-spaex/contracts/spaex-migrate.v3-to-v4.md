# Contract: `spaex migrate` v3 → v4 leg

**Spec**: 014
**Extends**: [`../../013-add-cli-and-molecule-rename/contracts/haex-migrate.v2-to-v3.md`](../../013-add-cli-and-molecule-rename/contracts/haex-migrate.v2-to-v3.md)
**Location in code**: `src/spaex/migrate/transform.py::v3_to_v4()` (and dispatch in `src/spaex/cli/migrate.py`)

The migrate chain becomes v1 → v2 → v3 → v4. The v1→v2 and v2→v3 transforms are preserved unchanged; this contract specifies only the new v3→v4 leg.

## Inputs and dispatch

`spaex migrate` walks the operator-provided root. For every file it recognises, it identifies the manifest kind by shape:

| Detected kind | v3 shape marker | Handled here |
|---|---|---|
| consumer | `.haex-hive.json` with `haex_hive_version: "3"` | yes |
| publisher root | file named `manifest.json` with `haex_hive_version: "3"` at repo root or explicit path | yes |
| molecule | file named `manifest.json` under a molecule directory with `haex_hive_version: "3"` | yes |
| install lock | `.haex-hive/install.lock` with `haex_hive_version: "3"` | **no**, runtime output, regenerated by `spaex install`; migrate never touches it |

Any file that already reports `spaex_version: "4"` is a no-op (idempotency, exit 0).

Any file with `haex_hive_version` in `{"1", "2"}` is routed through the v1→v2 or v1→v2→v3 legs first, then the v3→v4 leg. The final proposal is always v4.

## Transform semantics

For each recognised kind:

1. Rename top-level field `haex_hive_version: "3"` to `spaex_version: "4"`.
2. For consumer manifests: rename top-level `haex_hive_min_version` (if present) to `spaex_min_version` and apply the min-version-bump rule:
   - Exact `3.X.Y` → `4.X.Y`
   - Lower-bound `>=3.X.Y` → `>=4.0.0`
   - Any other form → refuse with `unsupported-min-version-constraint`, naming the offending constraint. No proposal is written for this file.
3. All other fields (including `identity`, `compounds`, `molecules`, `atoms`, `paths`, `source`, `revision`, etc.) pass through byte-identical modulo JSON reserialization.

The transform is **pure** in the sense of Principle VI: given identical input, it emits identical output. No timestamps, no host state, no random values.

## Proposal placement

Local (repo-rooted) proposals only. Remote (immutable-SHA publisher) placement is out of scope for Spec 014, matching the Spec 013 deferred T044R / T054R tasks.

| Input file (v3) | Proposal file (v4) |
|---|---|
| `.haex-hive.json` | `.spaex.json.migrated` (sibling next to `.haex-hive.json`) |
| Publisher root `manifest.json` | `manifest.json.migrated` (sibling next to the source) |
| Molecule `manifest.json` | `manifest.json.migrated` (sibling next to the source) |

Proposal files are written under the invocation's temp-file/proposal registry from Spec 013 (`src/spaex/migrate/registry.py`). A failure inside the invocation rolls back every registered proposal.

## Adoption instructions

Printed alongside the unified diff, per input:

- **Consumer**: `mv .spaex.json.migrated .spaex.json && rm .haex-hive.json`
- **Publisher / molecule `manifest.json`**: `mv manifest.json.migrated manifest.json`
- **Runtime state**: `rm -rf .haex-hive/  # regenerated by spaex install`

## Exit-code precedence (preserved from Spec 013)

- **0**: success, or all-v4 no-op.
- **1**: mixed (at least one proposal produced AND at least one refusal).
- **2**: hard refusal without any proposal.

`--dry-run` and `--check` semantics are unchanged from the Spec 013 contract.

## Contract tests (Phase 3)

The following unit tests MUST pass:

- **CT-014-M-01**: `v3_to_v4({"haex_hive_version": "3", "identity": "x.y", "compounds": []}, "consumer")` returns `{"spaex_version": "4", "identity": "x.y", "compounds": []}`.
- **CT-014-M-02**: `v3_to_v4({"haex_hive_version": "3", "haex_hive_min_version": "3.2.0", "identity": "x.y", "compounds": []}, "consumer")` returns the same shape with `spaex_min_version: "4.2.0"`.
- **CT-014-M-03**: `v3_to_v4({"haex_hive_version": "3", "haex_hive_min_version": ">=3.2.0", ...}, "consumer")` produces `spaex_min_version: ">=4.0.0"`.
- **CT-014-M-04**: `v3_to_v4({"haex_hive_version": "3", "haex_hive_min_version": "~2.0.0", ...}, "consumer")` raises `unsupported-min-version-constraint("~2.0.0")`.
- **CT-014-M-05**: Idempotency: `v3_to_v4({"spaex_version": "4", ...}, "consumer")` returns unchanged input.
- **CT-014-M-06**: Publisher-root transform preserves `molecules{}` map byte-for-byte modulo the two field renames.
- **CT-014-M-07**: Molecule transform preserves `atoms{}` category map byte-for-byte.
- **CT-014-M-08**: Determinism: two invocations with identical input return identical output (bit-for-bit after JSON canonicalization).

## Integration test (Phase 3)

- **IT-014-M-01**: On a fixture v3 repo (consumer + publisher + one molecule), `spaex migrate` emits three `.migrated` sibling files. Adopting each per the printed instructions and running `spaex install` produces a valid `.spaex/install.lock` with `spaex_version: "4"`.
