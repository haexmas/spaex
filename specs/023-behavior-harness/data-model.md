# Data Model: Behavior Harness (Phase 1)

Formalizes the entities identified in `spec.md` §Key Entities. Field types are documented at the domain level; Python types listed for implementation guidance.

## Entities

### Behavior Fragment

Atomic unit contributed by an atom. Backed by one file on disk.

| Field | Type | Origin | Notes |
|-------|------|--------|-------|
| `id` | string, `[a-z0-9][a-z0-9-]*` | YAML header | Fragment-local; molecule scope is inferred from filesystem location |
| `molecule_id` | string | Filesystem path segment | Not stored in header; derived from `.spaex/constitution.d/<molecule-id>/…` |
| `atom_source` | string | YAML header | Which atom within the molecule owns the fragment (informational, for provenance) |
| `modality` | enum: `MUST` \| `MUST_NOT` \| `SHOULD` \| `SHOULD_NOT` \| `MAY` \| `MAY_NOT` \| `null` | YAML header | Optional; when null, Composer infers from body |
| `tags` | list<string> | YAML header | Optional; Composer MAY use for grouping |
| `body` | string (Markdown) | Everything after the header | RFC-2119 convention in prose |
| `body_sha256` | bytes(32) | Computed | Whitespace-normalized SHA256 (per research.md §7); used in Clarification keys |

**Validation rules**:
- `id` MUST match `[a-z0-9][a-z0-9-]*` (kebab-case, no leading dash).
- `id` MUST be unique within its `molecule_id` scope.
- If `modality` is declared in the header and a top-level directive in the body carries a contradictory keyword, the pre-check emits a warning; body is authoritative.
- `body` MUST NOT be empty.

**Lifecycle**:
1. Authored inside a molecule source tree.
2. Materialized to `.spaex/constitution.d/<molecule-id>/<id>.md` at install time (Spec 017 molecule-store extraction).
3. Read by the mechanical pre-check.
4. Read by the Composer.
5. Persists on disk between installs; only removed when the contributing molecule is removed.

### Composed Constitution

The single spaex-owned artifact at `<repo-root>/.spaex.md`.

| Field | Type | Origin | Notes |
|-------|------|--------|-------|
| `path` | filesystem path | Constant | Always `<repo-root>/.spaex.md` |
| `header` | string | Static, from Composer prompt | "This file is generated by `spaex install`…" |
| `sections` | ordered map: modality → list<ComposedClause> | Composer | Only non-empty sections rendered |
| `source_hash` | string | Computed | SHA256 of canonical records containing every fragment field used by validation, Composer, or provenance, including normalized body content |
| `build_input_hash` | string | Computed | SHA256 of the effective Composer prompt content, prompt version, and valid clarification keys and answers |

**Validation rules**:
- MUST be regenerated whenever `source_hash` diverges from the on-disk fragment set.
- MUST be a plain Markdown file, no per-runtime dialects.
- MAY be absent when the fragment set is empty (FR-017d).

**Lifecycle**:
1. Composer produces content.
2. Written atomically by `spaex install` (write to `.spaex.md.tmp`, rename over `.spaex.md`).
3. Developer stages via git.
4. Committed as version-controlled content.
5. Read at runtime by any agent that has run the global bootstrap.

### Composed Clause

A single rendered directive inside `.spaex.md`.

| Field | Type | Origin | Notes |
|-------|------|--------|-------|
| `modality` | enum (same as Fragment.modality without null) | Composer | Section this clause lives under |
| `text` | string | Composer | Directive text, prose |
| `provenance` | list<ProvenanceRef> | Composer | One or more entries; 2+ when identical duplicates were deduped |

### ProvenanceRef

| Field | Type | Origin | Notes |
|-------|------|--------|-------|
| `molecule_id` | string | Fragment location | |
| `fragment_id` | string | Fragment.id | |
| `atom_source` | string | Fragment.atom_source | |
| `preset` | string \| null | `.spaex.json` composition profile | For the Phase B named-preset support (spec 019); null in MVP |

Rendered inline as `_[from `<molecule-id>/<fragment-id>`]_`.

### Constitution Clarification

Persisted operator answer to a Composer question about semantic overlap.

| Field | Type | Origin | Notes |
|-------|------|--------|-------|
| `key` | string (hex) | Computed per research.md §7 | SHA256 hex of sorted `<molecule-id>/<fragment-id>\|<body_sha256>` entries |
| `question` | string | Composer at ask-time | Human-readable question |
| `cited_fragments` | list<{molecule_id, fragment_id, body_sha256}> | Composer at ask-time | Fragments the question referred to |
| `answer` | string | Operator | Free-form; consumed by next Composer run |
| `asked_at` | ISO-8601 timestamp | System | Provenance |
| `answered_at` | ISO-8601 timestamp | System | Provenance |

**Storage**: `.spaex/clarifications.json`, one top-level object with entries keyed by `key` (research.md §10).

**Validation rules**:
- `key` MUST match its recomputed value from `cited_fragments`; mismatch invalidates.
- `answer` MUST be non-empty.

**Lifecycle**:
1. Composer detects semantic overlap or contradiction between fragments.
2. Question presented to operator; answer captured.
3. Entry persisted keyed by `key`.
4. Next Composer run recomputes `key` from current fragments. Match → apply answer without asking. Mismatch → discard entry, ask again.

### Project-Local Fragment

A fragment contributed by the project itself, not by a pinned molecule.

**Storage options** (per spec FR-018):
- Inline in `.spaex.json` under `constitution.local_fragments[]`, each entry a full fragment (header fields + body).
- File reference under a project directory such as `.spaex/local-fragments/<fragment-id>.md`, listed by path in `.spaex.json`.

**Treatment**: materialized at install time into a synthetic molecule scope `_project`, so ids become `_project/<fragment-id>`. Runs through identical mechanical pre-check and Composer paths as atom-provided fragments (FR-019).

**Constraint**: `_project/<fragment-id>` is a distinct emitted identity, but
the additive-only comparison key for a project-local fragment is its
`fragment_id`. A local `id: x` conflicts with every atom-provided
`<molecule-id>/x`, regardless of molecule, and install aborts with a diagnostic
listing the matching atom fragments and the additive-only remedy. This rule is
separate from atom identity paths and is deterministic even when several
molecules use the same fragment id.

### Global Bootstrap Block

Static content spaex writes into the user's per-runtime global instruction file.

| Field | Type | Origin | Notes |
|-------|------|--------|-------|
| `version` | integer | Constant per spaex release | Currently `1` |
| `content` | string (Markdown) | Constant per version | See research.md §4 |
| `start_marker` | string | Computed | `<!-- spaex-bootstrap:start version="<version>" -->` |
| `end_marker` | string | Constant | `<!-- spaex-bootstrap:end -->` |
| `target_paths` | list<filesystem path> | Runtime resolvers | Per-user, per-runtime files resolved from `CODEX_HOME` and Gemini `context.fileName` (research.md §3) |

**Lifecycle**:
1. Operator runs the bootstrap installer subcommand for a chosen set of runtimes.
2. Installer preflights each target path; if the file exists, it validates that any markers form exactly one ordered pair.
3. If a block already exists: read its `version` attribute. If same as current, no-op. If older, replace block content in-place.
4. If no block exists: append the block to the file (create file if missing).
5. On removal (`spaex uninstall --global`), the block is deleted along with its markers, and content outside the markers is preserved verbatim.

## Relationships

```text
Molecule (existing entity, Spec 007)
   └── contributes ──▶ Behavior Fragment (0..N)
                          └── materialized to .spaex/constitution.d/<molecule-id>/<id>.md

.spaex.json  (existing entity)
   ├── declares pinned Molecules → those contribute Behavior Fragments
   └── declares Project-Local Fragments (0..N) → synthetic molecule scope "_project"

Behavior Fragment (N)
   └── input to ──▶ Composer
                     ├── writes ──▶ Composed Constitution (1)  →  .spaex.md
                     └── writes/updates ──▶ Constitution Clarification (0..N)  →  .spaex/clarifications.json

Composed Constitution
   ├── contains ──▶ Composed Clause (0..N)
   │                   └── has ──▶ ProvenanceRef (1..N)
   └── read by ──▶ Agent Runtime (via Global Bootstrap Block indirection)

Global Bootstrap Block (1 per user per runtime)
   └── points agent to ──▶ .spaex.md in cwd
```

## State transitions

- `Behavior Fragment: absent → materialized` on `spaex install` after `spaex add <molecule>`.
- `Behavior Fragment: materialized → absent` on `spaex install` after `spaex remove <molecule>`.
- `Composed Constitution: fresh` when regenerated with matching source_hash.
- `Composed Constitution: stale-unresolved` after `spaex add/remove` per Clarification Q2 (Composer flagged contradictions but write went through as warning).
- `Composed Constitution: stale-fresh` when fragments changed but Composer has not yet re-run (User Story 6 acceptance scenario 3).
- `Constitution Clarification: current` when recomputed key matches stored key.
- `Constitution Clarification: invalidated` when keys diverge; next Composer run discards and re-asks.
- `Global Bootstrap Block: absent | v1 | v2+` per runtime; upgrade path in-place, no consumer action needed.
