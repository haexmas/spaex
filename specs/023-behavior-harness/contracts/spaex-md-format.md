# Contract: `.spaex.md` (Composed Constitution) Format

The single spaex-owned artifact at `<repo-root>/.spaex.md`. Produced by the Composer, committed by the developer, read by any agent runtime that has run the global bootstrap.

## File location

`<repo-root>/.spaex.md`

Where `<repo-root>` is determined by walking up from the current working directory until a `.git` directory or the filesystem root is reached (matches existing spaex convention for locating project roots).

## Header

Every generated file begins with:

```markdown
<!-- spaex-composed:source_hash="<sha256-hex>" version="1" -->
# spaex Behavior Harness

_This file is generated by `spaex install`. Do not edit by hand._
_Change fragments in `.spaex/constitution.d/` and re-run install._
```

The `spaex-composed` HTML comment carries drift-detection metadata:
- `source_hash`: SHA256 hex of the ordered fragment set that produced this content (research.md §5).
- `version`: format version, currently `1`; bumps invalidate any tooling that parses the file (Composer tolerates the previous version for one release cycle).

Content outside the metadata comment is human-readable Markdown.

## Body structure

Sections rendered in modality order, only non-empty sections included:

```markdown
## MUST

- <clause text>. _[from `<molecule-id>/<fragment-id>`]_
- <clause text>. _[from `<molecule-id>/<fragment-id>`, `<molecule-id>/<fragment-id>`]_

## SHOULD

- <clause text>. _[from `<molecule-id>/<fragment-id>`]_

## MAY

- <clause text>. _[from `<molecule-id>/<fragment-id>`]_
```

Sections use `##` (H2) headings, in the order `MUST`, `MUST_NOT`, `SHOULD`, `SHOULD_NOT`, `MAY`, `MAY_NOT`.

Each clause is a top-level bullet, followed by an italicized provenance suffix.

## Clause rendering rules

- Text is prose written by the Composer, synthesizing overlapping fragment bodies. Line breaks inside a clause are preserved as spaces (no hard-wrapping) to keep the file diff-friendly.
- Provenance suffix is inside italic underscores: `_[from `<molecule-id>/<fragment-id>`]_`.
- Multiple provenances (from dedup) are comma-separated: `_[from `strict-testing/no-mocks`, `qa-baseline/mocks-forbidden`]_`.
- Backticks preserve fragment identifier verbatim.

## Empty-state behavior

- If the project has zero active fragments, `.spaex.md` is either absent from the repo (preferred) or a minimal file containing only the header comment and a note "No behavior harness declared for this project.". Both forms are valid per FR-017d.

## Provenance regex

For the trace command (contracts/cli-surface.md `spaex constitution trace`), clauses match the following stable regex:

```regex
^- (?P<text>.+?)\. _\[from (?P<provenance>`[^`]+`(?:, `[^`]+`)*)\]_$
```

The Composer prompt (contracts/composer-interface.md) explicitly instructs the LLM to emit clauses matching this pattern.

## Byte-identity guarantee (SC-003)

For the same input fragment set (same bodies, same identifiers, same clarifications answered), the Composer prompt is engineered to produce byte-identical output across independent invocations by:
1. Fixing section order.
2. Fixing bullet order within sections (Composer sorts by provenance identifier lexicographically).
3. Requiring the LLM to output a canonical form (no synonyms swap, no reordering).
4. Persisting all operator answers so no non-deterministic clarification affects output.

If the LLM produces non-byte-identical output despite these constraints, the reproducibility test flags it; a follow-up may add a post-processing normalization pass. Not blocking for MVP.

## What agents do with this file

Agents that have run the global bootstrap read `.spaex.md` and treat its content as project-level instructions:
- `MUST` clauses are treated as inviolable constraints.
- `SHOULD` clauses are treated as strong defaults, overridable only with operator justification.
- `MAY` clauses are treated as permissive guidance.

The exact runtime behavior is a property of each agent runtime, not of spaex. spaex's contract ends at "emit the composed constitution in this format at this path".
