# Contract: Composer Interface

Defines how spaex invokes the LLM Composer, what the Composer's canonical system prompt requires, and what it returns.

## Invocation modes

Two paths, tried in the order documented in research.md §1 and §2:

### 1. Direct API via litellm

spaex constructs a litellm request using:
- Model id: `SPAEX_LLM_MODEL` if set, otherwise the runtime's canonical model.
- System prompt: the canonical Composer prompt (see below).
- User message: JSON-serialized composer input (see below).
- Response format: text (Composer prompt requires strict Markdown output).
- Timeout: `SPAEX_COMPOSER_TIMEOUT` seconds (default 30).

### 2. CLI shell-out to installed agent runtime

spaex invokes `claude` (or `codex`, `gemini`) as a subprocess with:
- stdin: composer input as a single message.
- args: runtime-specific for a one-shot non-interactive session.
- stdout captured; parsed as if it were the direct-API response.

Timeout applied via subprocess timeout.

## Composer input

Passed as a single UTF-8 JSON document:

```json
{
  "spaex_version": "4.2.0",
  "composer_prompt_version": "1",
  "fragments": [
    {
      "molecule_id": "<molecule-id>",
      "fragment_id": "<fragment-id>",
      "atom_source": "<atom-source>",
      "modality": "MUST|MUST_NOT|SHOULD|SHOULD_NOT|MAY|MAY_NOT|null",
      "tags": ["..."],
      "body": "<Markdown body>",
      "body_sha256": "<hex>"
    }
  ],
  "clarifications": [
    {
      "key": "<hex>",
      "question": "<verbatim>",
      "cited_fragments": [
        {"molecule_id": "...", "fragment_id": "...", "body_sha256": "..."}
      ],
      "answer": "<operator answer>"
    }
  ]
}
```

`fragments` are sorted lexicographically by the full scoped key
`<molecule-id>/<fragment-id>` for byte-identity determinism.

## Composer output

The Composer produces one of two response shapes:

### Shape A: composed constitution (no new questions)

```markdown
<<<SPAEX-COMPOSER-BEGIN>>>
{
  "type": "composed",
  "questions": []
}
<<<SPAEX-COMPOSER-END>>>

<!-- spaex-composed:source_hash="<sha256-hex>" build_input_hash="<sha256-hex>" version="1" -->
# spaex Behavior Harness

_This file is generated by `spaex install`. Do not edit by hand._
_Change fragments in `.spaex/constitution.d/` and re-run install._

## MUST
- ...
## SHOULD
- ...
## MAY
- ...
```

The sentinel-wrapped JSON at the top is parsed and stripped; what follows is the raw `.spaex.md` content.

### Shape B: clarification questions (composed constitution NOT yet written)

```markdown
<<<SPAEX-COMPOSER-BEGIN>>>
{
  "type": "questions",
  "questions": [
    {
      "kind": "overlap|contradiction",
      "cited_fragments": [
        {"molecule_id": "...", "fragment_id": "..."}
      ],
      "question": "<human-readable question>"
    }
  ]
}
<<<SPAEX-COMPOSER-END>>>
```

spaex presents each question to the operator and stages the answers in memory.
It re-invokes the Composer once with the staged `clarifications` array. The
clarification round is bounded to one Shape B response per build: a second
Shape B response is an `invalid-output` failure, so repeated questions cannot
block installation. Staged answers are written to
`.spaex/clarifications.json` only after a verified Shape A succeeds; a timeout,
invalid response, or any other abort leaves the previously tracked file
unchanged.

## Canonical system prompt (contract)

The system prompt lives at `src/spaex/behavior/composer/prompt.py` as a string constant. Its version is `composer_prompt_version` in the input. The prompt MUST:
- Instruct the LLM to produce ONE of the two response shapes above.
- Instruct the LLM to resolve effective modality from the body directive when it conflicts with the header; the body wins, while the header remains available to the mechanical pre-check.
- Instruct the LLM to sort clauses within each modality section by the full scoped provenance key `<molecule-id>/<fragment-id>`.
- Instruct the LLM to use the lexicographically sorted list of full provenance keys as the tie-breaker for merged clauses, followed by normalized clause text.
- Instruct the LLM to use the exact clause template: `- <text>. _[from `<molecule-id>/<fragment-id>`]_`.
- Instruct the LLM to omit empty modality sections.
- Instruct the LLM to synthesize semantic overlaps (same rule stated differently) into a single clause with combined provenance.
- Instruct the LLM to flag semantic contradictions (contradictory MUST across molecules) as a `contradiction` question in Shape B, never silently emit both.
- Instruct the LLM to include `source_hash` and `build_input_hash` in the `spaex-composed` comment. `source_hash` is the SHA256 hex of concatenated `<molecule-id>/<fragment-id>|<body_sha256>` lines sorted lexicographically. `build_input_hash` is the SHA256 hex of the canonical Composer prompt version plus the valid clarification keys and answers.
- Require spaex to compute both expected hashes outside the LLM and reject Shape A when either returned value is missing or mismatches. The LLM-provided values are claims to verify, not trusted drift metadata.

The prompt is versioned. `composer_prompt_version` in the input is the version spaex is currently shipping. On prompt-version bumps across spaex releases, all persisted clarifications are treated as invalidated (research.md §12; documented in spec Assumptions).

## Project-level prompt override

Consumers who want to customize the Composer's behavior for their project MAY create `.spaex/composer-prompt.md`. If present, its content overrides the canonical prompt for that project only. Overriding the prompt takes ownership of clarification-flow behavior for that project (Assumptions).

The override file MUST include the same output-shape contract; spaex validates that Shape A and Shape B parsers succeed on the override's first invocation and aborts with a diagnostic if not.

## Failure surface

Every failure falls into one of the categories documented in research.md §8 and contracts/cli-surface.md exit codes 30-34. The failure includes:
- Category name.
- Detailed message.
- (For invalid-output) path to raw LLM response written to `$SPAEX_COMPOSER_LOG` (default `.spaex/composer.log`).

Silent degradation to raw concatenation is explicitly forbidden (FR-012a).

## Determinism aids

- Temperature setting: 0.0 for direct-API mode. CLI shell-out output is parsed and canonicalized by spaex using the same section order, full-provenance sort, whitespace normalization, and metadata verification as direct-API output.
- Seed: passed when the API supports it.
- Canonical output shape enforced by parser: rejection of malformed output triggers `invalid-output` failure. Semantic wording changes that survive parsing are surfaced as a normal artifact diff; unchanged input fingerprints never cause an implicit rewrite.
