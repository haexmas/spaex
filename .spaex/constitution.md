- Prefer the standard library and existing project dependencies before adding a new package, justifying any dependency addition by a real capability or maintenance benefit. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Raise specific exceptions, catch only exceptions that can be handled at that layer, and preserve the original cause with exception chaining when translating errors. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Use context managers for resources such as files, locks, and transactions. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Follow the repository's supported Python versions and style configuration; use the project's configured formatter, linter, type checker, and test runner — instead of introducing competing project-wide tooling — and run them, together with the relevant tests, before handing off a change; absent project-specific commands, a reasonable baseline is `python -m compileall` plus the configured test and static-check commands, confirming that the test runner actually discovers the intended files. _[from `com.github.haexmas.atoms.coding-guideline-python/python`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Exercise successful and failure behavior while asserting the exception type and meaningful details, without over-specifying incidental message formatting. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Keep parametrized cases focused and readable, adding a new case only when it demonstrates a distinct boundary or regression. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Keep tests easy to read, fast enough to run frequently, and honest about what they do not cover, remembering that a passing test is evidence only for the behavior it actually exercises. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Test coroutines with the project's supported async test tooling, and test cancellation, timeout, cleanup, and ordering assumptions when they affect correctness. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Use `unittest` or the project's chosen test framework consistently, making fixture setup and cleanup explicit through context managers and framework cleanup hooks so that a failing test cannot leak files, connections, processes, or patches into the next test. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- A change of about 100 net lines should be treated as a useful review-size warning and a change approaching 1000 lines as a strong prompt to split the work or agree on the larger change in advance, with generated code, mechanical renames, and required migrations identified as legitimate exceptions. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- A change that clearly improves maintainability and correctness should be preferred over theoretical perfection, making the smallest reversible change that provides evidence about the next decision when a design is uncertain. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- A file should have one primary reason to change, being split when it has unrelated responsibilities, independent public concepts, different change owners, or tests that are difficult to isolate, rather than solely to make files shorter. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- An existing repository's documented structure, naming scheme, or size convention should be followed unless the task explicitly changes that convention, since this guidance supplies defaults rather than a reason to reformat or reorganize an entire codebase. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Broad formatting or mechanical refactors should be separated from behavior changes when possible, since mixed diffs make review, debugging, rollback, and blame less reliable. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Code should be named after its domain meaning and behavior rather than relying on a comment to explain an otherwise opaque `data`, `helper`, or `process` function. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Code should be organized around cohesive domain or feature boundaries where the codebase supports it, rather than creating folders only for superficial symmetry such as putting every small class, interface, or helper in its own folder. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Comments should explain why a non-obvious decision exists, what invariant must be preserved, or which external constraint applies, rather than narrating code that could be made clear through structure and naming, and should be updated when the behavior changes. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Dependencies should be kept directed and understandable, avoiding circular imports, hidden global state, and a domain layer that knows about infrastructure details, putting I/O, framework adapters, and process wiring at the edges when the architecture calls for such a separation. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Each change should be kept self-contained and easy to review, with production code, relevant tests, documentation, and configuration belonging together when they describe the same behavior, and independent refactors or unrelated cleanups split into separate changes. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Each function should have one coherent responsibility at one level of abstraction, extracting a helper when it gives a meaningful name to a concept, makes a branch independently testable, or removes repeated logic, not merely because it crossed an arbitrary line count. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Early returns or named helpers should be preferred when they make the main path easier to follow, reducing nesting without scattering one simple operation across many microscopic functions. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Files that may exceed the 500 LoC boundary, such as generated files, vendored code, and snapshots, should be excluded from file-size assessment. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Public module interfaces should be kept narrow and intentional, hiding implementation details behind the smallest stable API callers need rather than re-exporting everything or creating pass-through modules that add no boundary. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Related tests should be kept close to the behavior they verify according to the language and repository convention, along with documentation, fixtures, and call sites, so that a module split is not left misleadingly incomplete. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Repeated behavior should be refactored when the shared rule is real and the abstraction makes both callers clearer, keeping the abstraction close to the domain that owns it rather than letting a generic utility module become a dumping ground. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Side effects should be kept at visible boundaries so that pure calculations and decisions are easy to test without a database, network, filesystem, clock, or global mutable state. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Smaller soft thresholds, such as a function or method beyond roughly 40-60 lines or nesting deeper than roughly three levels, should be used as prompts for a deliberate review look rather than as automatic failures or mandatory limits. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Tests should be added or updated with behavior changes, testing observable behavior and important failure modes rather than private implementation details, since a test is useful only when it can fail for a real regression. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- The repository's formatter, static checks, and relevant tests should be run before handoff, with what was run and any unavailable or skipped checks reported rather than presenting a green-looking diff as an unverified claim of success. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- For any question about the codebase — what something does, where it lives, how pieces relate, whether an existing artifact already satisfies a request, or how to trace a symptom to its source, including exploratory lookups incidental to a larger task — run a bounded `graphify query "<intent>" --budget <N>` (or `graphify path`/`graphify explain` for one specific relationship or symbol) before a raw `grep`/`rg` search or broad file reads, starting around an 800–1500 token budget and raising it only if the returned relationships are insufficient; the only exemption is a local one-file edit at a symbol whose location is already known from earlier in the same task. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- Preserve in the resulting context map, when available, the task intent and token budget, the selected files and symbols, the relevant edge or call relationship, source locations for every claim, and an explicit note when the result is truncated or the consultation failed. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- Propose extracting and reusing a shared implementation when six or more identical lines of the same logic appear across candidates, as rough guidance rather than a hard cutoff; operator judgment overrides it. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Before writing new code, read the task and the code it touches and trace the real flow end to end, then climb a laziness ladder in order: confirm the feature is actually needed (YAGNI), check whether it already exists in the codebase and reuse it, check whether the standard library covers it, check for a native platform feature, check an already-installed dependency, consider whether it can be a single line, and only then write the minimum code that works. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- Fix a reported bug at its root cause rather than its symptom: grep every caller of the function being touched and fix the shared function once, rather than patching only the path the report names and leaving a sibling caller still broken. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- Prefer deletion over addition, boring solutions over clever ones, and the fewest files possible; once the problem is understood, prefer the shortest working diff; question complex requests by asking whether the need is already covered by something simpler; and when two standard-library approaches are otherwise equally sized, pick the edge-case-correct option rather than the flimsier one. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_

## SHOULD_NOT

- Avoid `any`; use a precise type, a generic, or `unknown` followed by explicit narrowing instead, and keep any necessary untyped escape hatch local with an explanation of why it is necessary. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Avoid real network calls or services, shared mutable state, order dependence, uncontrolled random values, and arbitrary timer sleeps in tests. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Avoid clever metaprogramming when ordinary functions and classes suffice. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Avoid expensive work, network access, and surprising side effects at module import time, unless the project explicitly uses that pattern. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- A universal maximum line count for functions, files, or pull requests should not be enforced, since domain complexity, cohesion, control flow, and the number of reasons to change are more meaningful than a line count. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Artificial wrappers, blank lines, or extra files should never be added only to satisfy a line-count threshold. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Files should not be padded up toward the 500 LoC boundary, since it is a maintainability constraint rather than a target. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Two things should not be abstracted together merely because they look similar; establish that they share the same behavior, ownership, change reason, and invariants first, since a small amount of local duplication is preferable to a premature generic abstraction that couples unrelated callers. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Avoid over-extracting fewer than five purely structural matching lines, such as setup, error-wrapping, or adapter boilerplate, and usually leave matches found only inside test files alone unless they are helper functions; these are rough guidance, not hard cutoffs, and operator judgment overrides them. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Leave duplicated arrange/assert/setup blocks across test cases alone rather than consolidating them, since each test's setup documents that test's assumptions in place and consolidating them can obscure regressions; this does not apply to helper functions living inside test files, which remain subject to the ordinary consult-the-graph-before-authoring rule. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Avoid a new dependency when it can be avoided, and avoid adding boilerplate nobody asked for. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
